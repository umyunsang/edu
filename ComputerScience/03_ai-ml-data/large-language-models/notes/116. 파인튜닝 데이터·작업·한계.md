> [!NOTE]
> 파인튜닝은 사전 학습 가중치를 출발점으로 특정 작업·도메인 데이터에 추가 학습을 수행하는 전이 학습의 한 형태다. 데이터 품질과 평가 설계가 모델 선택만큼 중요하다.

---

## 적용 전에 판단할 것

| 질문 | 파인튜닝이 맞는 경우 | 먼저 시도할 대안 |
| :-- | :-- | :-- |
| 출력 형식 | 반복적으로 같은 스타일·톤·형식이 필요 | 명확한 출력 스키마와 예시 |
| 오류 유형 | 프롬프트만으로 고치기 어려운 반복 오류 | 프롬프트 엔지니어링 |
| 엣지 케이스 | 많은 사례를 일관되게 학습해야 함 | 프롬프트 체이닝 |
| 새 행동 | 말로 설명하기 어려운 작업 패턴 | 함수 호출과 도구 구성 |

<details>
<summary>원문이 권하는 투자 순서</summary>

먼저 프롬프트 엔지니어링, 작업을 나누는 프롬프트 체이닝, 함수 호출로 성능을 개선해 본다. 그래도 반복적 품질 문제가 남을 때 데이터 준비와 학습 비용을 감수할지 판단한다.

</details>

| 평가 | 검증 데이터로 비교하고 필요 시 반복 | 과적합, 범용성 저하 |

## 파인튜닝 기법의 차이

<Tabs>
  <Tab label="Full">모델 전체 가중치를 업데이트하며 대규모 데이터와 컴퓨팅 자원이 필요하다.</Tab>
  <Tab label="Partial">일부 계층만 학습하고 나머지 계층은 고정한다.</Tab>
  <Tab label="Prompt·Prefix">입력에 추가되는 학습 가능한 표현으로 출력을 조정한다.</Tab>
  <Tab label="Adapter">작은 네트워크를 덧붙이고 기존 모델 가중치는 유지한다.</Tab>
  <Tab label="LoRA">저차원 매개변수를 학습해 업데이트 비용을 줄인다.</Tab>
</Tabs>

> [!IMPORTANT]
> 기법 이름만으로 성능을 보장할 수 없다. 데이터 크기, 모델 구조, 작업 특성, 사용할 추론 환경을 함께 보고 선택한다.

## JSONL 학습 데이터

**핵심:** 한 줄에 하나의 JSON 객체를 두고, 채팅 데이터는 역할과 내용이 있는 메시지 배열로 구성한다.

```json
{"messages":[{"role":"system","content":"행동 지침"},{"role":"user","content":"입력 예시"},{"role":"assistant","content":"목표 응답"}]}
```

| 검증 항목 | 확인 내용 |
| :-- | :-- |
| 구문 | 각 줄이 독립적인 JSON 객체인지 |
| 역할 | system, user, assistant 역할이 올바른지 |
| 대응 | 입력과 목표 응답이 작업 의도에 맞는지 |
| 품질 | 사실 오류·모순·불필요한 민감정보가 없는지 |
| 분할 | 훈련 데이터와 검증 데이터를 구분했는지 |

> [!CAUTION]
> 원문 설명은 파일을 `prompt`와 `completion` 형태라고 쓰지만, 이어지는 채팅 예제는 `messages` 배열을 사용한다. 대상 모델·엔드포인트의 현재 데이터 스키마를 기준으로 검증해야 한다.

## 파일 업로드와 작업 생성

| 순서 | 클라이언트 기반 원문 예 | 필요한 식별자 |
| :-- | :-- | :-- |
| 파일 업로드 | `client.files.create`, 목적 `fine-tune` | 업로드된 훈련 파일 ID |
| 작업 생성 | `client.fine_tuning.jobs.create` | 기반 모델, 훈련 파일 |
| 상태 조회 | `client.fine_tuning.jobs.retrieve` | 파인튜닝 작업 ID |
| 결과 사용 | 채팅 요청의 모델에 파인튜닝 모델 ID 지정 | 완료된 모델 ID |

<details>
<summary>평가 후 반복</summary>

작업 생성 성공만으로 완료가 아니다. 검증 데이터와 실제 사용 사례에서 결과를 평가하고, 오류 유형이 데이터 문제인지 설정 문제인지 분리한 뒤 데이터 준비 단계로 돌아간다.

</details>

## 레거시 API와 현재형 예제의 충돌

| 원문 표기 | 같은 구간의 다른 표기 | 주의점 |
| :-- | :-- | :-- |
| `FineTune.create` | `client.fine_tuning.jobs.create` | 서로 다른 SDK 세대 |
| `FineTune.retrieve` | `client.fine_tuning.jobs.retrieve` | 반환 객체 접근법도 다름 |
| `FineTune.list`, `cancel`, `events` | 클라이언트 작업 네임스페이스 | 메서드를 한 코드에서 혼합 금지 |
| `File.create` | `client.files.create` | 파일 API도 세대가 다름 |
| davinci·curie 기반 표 | 날짜가 붙은 GPT 모델 목록 | 지원 모델 목록이 한 시점에 고정되지 않음 |

> [!WARNING]
> 원문 표의 `retrieve(file_id)`·`delete(file_id)` 설명은 본문에서 다시 `fine_tune_id`와 조회·취소 동작으로 바뀐다. 이름과 동작이 충돌하며, `download(file_id)`도 파일 작업과 파인튜닝 작업을 한 표에 섞는다.

식별자 취급은 API 세대와 별개의 보안 경계다.

> [!DANGER]
> 원문에는 구체적인 파일 ID, 작업 ID, 파인튜닝 모델 ID를 코드에 직접 넣은 예가 있다. 이 노트는 해당 값을 재현하지 않는다. 실제 식별자는 실행 환경에서 받은 값을 저장·전달하고 공개 문서나 로그에 복사하지 않는다.

## 적용 사례와 한계

| 적용 사례 | 기대하는 변화 |
| :-- | :-- |
| 고객 서비스 | 특정 응답 스타일과 도메인 규칙 |
| 금융 뉴스·법률 문서 | 분야별 분류 |
| 질의응답·요약 | 작업 형식에 맞는 생성 |
| 생의학 텍스트 | 논문 분석·개체 인식 |

| 한계 | 대응 |
| :-- | :-- |
| 고품질 레이블 데이터 필요 | 수집·검수 기준과 오류 분류 정의 |
| 학습 비용과 시간 | 대안 기법과 예상 효익 비교 |
| 소량 데이터 과적합 | 별도 검증 세트와 조기 종료 검토 |
| 범용성 저하 | 기본 모델 대비 회귀 평가 |

> [!WARNING]
> 파인튜닝 가능 모델 목록, GPT 계열의 날짜 식별자, ada·babbage·curie·davinci의 규모와 상태는 모두 원문 시점 정보다. 현재 지원 여부나 매개변수 규모를 이 표에서 추정하지 않는다.

## 정리

- 파인튜닝은 프롬프트·체이닝·함수 호출을 검토한 뒤 투자할 선택지다.
- JSONL은 구문뿐 아니라 역할, 목표 응답, 데이터 분할까지 검증한다.
- 최소 10개, 권장 50–100개, 레거시 4에폭은 서로 다른 범주의 지표다.
- 레거시 `FineTune`와 클라이언트 기반 작업 API를 같은 구현에 섞지 않는다.
- 성능 향상과 함께 과적합, 비용, 범용성 저하를 평가한다.
