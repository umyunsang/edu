## 텍스트 요청과 대화 요청

**핵심:** 일반 텍스트 완성과 달리 채팅 요청은 대화 참여자의 역할과 발화 순서를 함께 전달한다.

| 구분 | 입력 | 출력 | 적합한 흐름 |
| :-- | :-- | :-- | :-- |
| 텍스트 완성 | 단일 텍스트 | 생성 텍스트 | 한 번의 지시와 결과 |
| Chat Completion | 메시지 목록 | assistant 메시지 | 문맥이 이어지는 상호작용 |

<Tabs>
  <Tab label="system">대화 전체의 행동 원칙, 어조, 전문성, 답변 길이 같은 초기 지침을 둔다.</Tab>
  <Tab label="user">사람의 질문과 요청을 담는다.</Tab>
  <Tab label="assistant">모델이 만든 답변을 기록해 다음 요청의 문맥으로 다시 전달한다.</Tab>
</Tabs>

> [!WARNING]
> 원문 앞부분의 역할 표는 system·user·assistant만 설명하지만 후반 호출 예제에는 developer 역할이 등장한다. 역할 목록이 서로 다른 API 세대의 예시임을 구분해야 한다.

| 단계 | 처리 | 다음 상태 |
| :-- | :-- | :-- |
| 1 | 역할과 내용으로 메시지 목록 구성 | 요청 문맥 완성 |
| 2 | 선택한 모델에 목록 전달 | assistant 응답 생성 |
| 3 | choices에서 message 확인 | 내용과 종료 이유 해석 |
| 4 | assistant 응답을 목록에 추가 | 후속 질문 문맥 갱신 |

## 요청을 만드는 세 단계

1. 사용할 모델을 정한다. 원문은 모델 선택이 출력과 요청 비용에 모두 영향을 준다고 설명한다.
2. 프롬프트의 목표와 필요한 정보를 작성한다.
3. 원하는 출력 유형을 지시하는 user 메시지를 구성한다.

> [!IMPORTANT]
> 메시지는 단순 문자열 묶음이 아니라 순서가 있는 대화 기록이다. 후속 질문 전에 이전 assistant 응답을 목록에 추가해야 대화 흐름을 이어 갈 수 있다.

<details>
<summary>연속 대화에서 문맥을 갱신하는 순서</summary>

- 첫 user 질문과 system 지침으로 요청한다.
- 반환된 assistant 내용을 출력하고 메시지 목록에 추가한다.
- 두 번째 user 질문을 같은 목록에 추가한다.
- 갱신된 전체 목록으로 다음 요청을 보낸다.

원문 실습은 첫 요청에 gpt-4o-mini, 두 번째 요청에 gpt-4를 사용한다. 이는 모델을 바꾼 예시이지 동일 모델 유지 규칙을 보여 주는 예시는 아니다.

</details>

## 생성 제어와 응답 해석

```html preview
<div style="font-family:system-ui,sans-serif;padding:20px">
  <div id="cards" style="display:flex;gap:14px;flex-wrap:wrap"></div>
  <script>
    var stats = [
      ['temperature', '0–2', 'Chat Completion 범위', 'var(--chart-2)'],
      ['stop', '최대 4개', '중단 문자열', 'var(--chart-1)'],
      ['n', '기본 1개', '생성 결과 수', 'var(--chart-5)']
    ];
    document.getElementById('cards').innerHTML = stats.map(function (s) {
      return '<div style="flex:1;min-width:150px;padding:16px;background:var(--card);' +
        'color:var(--card-foreground);border:1px solid var(--border);' +
        'border-radius:var(--radius)">' +
        '<div style="font-size:13px;color:var(--muted-foreground)">' + s[0] + '</div>' +
        '<div style="font-size:26px;font-weight:700;margin-top:4px">' + s[1] + '</div>' +
        '<div style="font-size:12px;font-weight:600;margin-top:4px;color:' + s[3] + '">' +
        s[2] + '</div>' +
        '</div>';
    }).join('');
  </script>
</div>
```

| 요청 필드 | 원문 설명 | 읽을 때의 경계 |
| :-- | :-- | :-- |
| model | 사용할 모델 이름 | 모델 선택은 출력과 비용에 영향 |
| messages | 역할과 내용의 대화 기록 | 순서와 누락 여부를 함께 확인 |
| temperature | 창의성 수준 | 다른 슬라이드의 범위와 충돌 가능 |
| max_tokens | 최대 생성 토큰 수 | 원문 시점의 문맥 한계와 구분 |
| top_p | 누적 확률 기반 다양성 제어 | temperature와 동시 변경을 경계 |
| frequency_penalty | 반복 단어 억제 | 음수·양수 범위 설명은 이 구간에 없음 |
| presence_penalty | 새로운 주제·단어 사용 제어 | 결과 보장값이 아님 |
| stop | 지정 문자열에서 생성 중단 | 모델별 현재 지원 여부는 별도 확인 |
| n | 한 요청에서 생성할 결과 수 | 값이 커질 때의 비용을 구분 |

| 응답 필드 | 의미 |
| :-- | :-- |
| id, created, model | 응답 식별자·생성 시점·사용 모델 |
| choices | 생성 결과 목록 |
| message | role과 content를 포함한 메시지 |
| finish_reason | stop, length 같은 종료 이유 |
| usage | 입력·출력·전체 토큰 사용량 |

> [!IMPORTANT]
> 반복적 대화에서는 불필요한 정보가 반복될 수 있고, 비용은 사용량에 따라 증가한다.

문맥 한계는 생성 결과 수와 다른 시점 정보다.

> [!CAUTION]
> 원문은 문맥 한계를 4,096–32,768 토큰으로 적는다. 특정 모델·시점에 종속된 값이므로 현재 모든 모델의 공통 한계로 일반화하지 않는다.

## system 지침의 설계 축

| 설계 축 | 원문 예시의 의도 |
| :-- | :-- |
| 태도 | 친절하고 격려하는 방식 |
| 전문성 | 컴퓨터 과학 전문가처럼 기술적으로 설명 |
| 중립성 | 객관적이고 편향되지 않은 응답 |
| 문체 | 셰익스피어 등장인물 같은 스타일 |
| 길이 | 100단어 이하의 간결한 답변 |
| 역할 | 초보자를 돕는 개인 트레이너 |
| 설명 수준 | 필요한 경우 예시를 포함한 상세 설명 |
| 정서 지원 | 불안하거나 힘든 사용자에게 지지적 응답 |

> [!TIP]
> 역할, 어조, 길이, 설명 수준을 한 문장에 뒤섞기보다 서로 다른 제약으로 분리하면 어떤 조건이 결과에 영향을 주었는지 확인하기 쉽다.

## 편집 작업을 메시지로 전환하기

원문은 별도 Edit API와 Chat Completion을 모두 소개하지만, 마지막 실습은 편집 목적을 user 메시지로 전달하는 방식이다.

<Tabs>
  <Tab label="교정">문법·철자 오류 수정, 명확성 개선</Tab>
  <Tab label="톤">격식체·일상체·전문적 문체로 변환</Tab>
  <Tab label="구조">두 문장 요약, 글머리표 구성, 간결화·확장</Tab>
  <Tab label="변환">번역, 시적 재구성, 시대 문체 변경</Tab>
  <Tab label="코드">리팩터링, 주석 추가, 구문 오류 수정</Tab>
</Tabs>

| 편집 입력 | 역할 |
| :-- | :-- |
| 원문 | 수정 대상 텍스트 |
| instruction 또는 user 지시 | 수행할 변환 |
| 생성 제어값 | 결과의 다양성과 길이 조정 |
| 반환 content | 수정된 텍스트 |

## 원문 API 충돌과 보안 경계

> [!WARNING]
> 원문에는 서로 다른 API 세대와 코드 오류가 함께 있다. ChatCompletion, Completion, 별도 Edit.create()와 openai.chat.completions.create()가 혼재하며, text-davinci-edit-001과 code-davinci-edit-001은 당시 예시로만 취급해야 한다. 또한 한 예제의 model=="gpt-4o-mini"는 대입 자리에 비교 연산자를 쓴 오류이고, Edit와 Chat Completion 설명의 temperature 범위도 서로 충돌한다. 변경한는, 중복 물음표, 비표준 따옴표도 원문 오류로 남아 있다.

보안 문제는 API 세대 충돌과 별도로 차단한다.

> [!DANGER]
> 두 실습 슬라이드는 키처럼 보이는 문자열을 소스 코드에 직접 넣는다. 이 노트는 해당 값을 재현하지 않고 원문 위험으로 기록한다.

<details>
<summary>이 구간을 현재 코드로 옮길 때 확인할 것</summary>

- 사용 중인 SDK 세대의 클라이언트 생성 방식
- 지원되는 역할 이름과 응답 객체 구조
- 모델별 문맥 길이와 출력 제한
- 폐기되거나 대체된 Edit 계열 API

</details>

## 정리

| 핵심 개념 | 의미 | 적용 또는 경계 |
| :-- | :-- | :-- |
| 메시지 목록 | 역할과 내용으로 구성된 대화 기록 | 이전 응답을 다시 넣어 문맥 유지 |
| system 지침 | 행동·어조·형식의 상위 조건 | 서로 다른 제약을 분리 |
| 생성 제어 | 다양성·길이·반복을 조정하는 필드 | 모델과 API 시점에 종속 |
| 응답 구조 | choices, message, usage로 결과 해석 | 종료 이유와 토큰 사용량 확인 |
| 편집 | 교정·톤·구조·번역·코드 변환 | 구형 Edit API와 채팅 지시를 구분 |
