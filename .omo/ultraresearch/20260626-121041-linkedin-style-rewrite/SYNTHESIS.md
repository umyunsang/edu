# Ultraresearch Synthesis: LinkedIn Style Rewrite

Workers: 7 research threads plus root web/local checks · Waves: 2 primary waves plus root expansion/closure · Sources: public LinkedIn posts, LinkedIn official help/business resources, Buffer/Hootsuite guidance, local repo evidence, Hugging Face public API/pages, W&B public GraphQL · Verifications: link and leakage checks after rewrite

## Executive Summary

The original drafts were broadly accurate but read like portfolio summaries. Actual LinkedIn developer/project posts are more effective when they start from one concrete problem or realization, show one artifact, state what changed, and end with a real question. Broad lists of equal-weight links weaken the CTA.

For this user's Korean LinkedIn voice, the strongest fit is not aggressive growth-copy. The rewrite should use modest first-person phrasing, concrete artifacts, direct proof links, and a soft question. Each post should stand alone even if the reader never clicks, while the link should point to the exact artifact rather than a repository root.

The deeper project research changes the narrative: this is not just "several GitHub projects." The coherent story is evidence-first AI/product work across civic agents, public-service model experiments, interaction publishing, a graph-structured learning archive, and proof-boundary workflow design.

## Findings by Theme

### Tone and Structure

- Use a hook that names the tension: "AI를 썼다"보다 "무엇을 검증 가능하게 남겼는가"가 stronger.
- Keep paragraphs short. One idea per block.
- Use "문제 → 만든 것/정리한 것 → 확인한 것 → 배운 것 → 질문" as the default structure.
- Avoid resume-style enumeration. Prefer a narrative about one artifact.

### Links and Proof

- Use one primary link per post. Secondary links can be placed after the main link or in a comment variant.
- For UMMAYA, docs/demo are better public proof than only the repo root.
- For DigitalPublishing, the live demo is the correct primary proof because the claim is experiential.
- For LG Aimers, link exact notes when making model-efficiency learning claims.
- For IlluOps, say "planning/evidence/reference repo" and link public-safe evidence surfaces only.
- For Hugging Face, link the exact model/dataset. Do not bury the model work behind the GitHub profile.
- For W&B, link `umyun3/GovOn` as experiment-tracking proof only. Do not infer metrics from project existence.

### LinkedIn Guidance

- LinkedIn official help says posts can include links and text up to 3,000 characters, and link previews may display when URLs are pasted.
- LinkedIn Business guidance recommends relevant hashtags, with 3-5 for Pages. For personal Korean developer posts, use fewer: 1-3 specific tags.
- Industry sources and public LinkedIn examples consistently favor self-contained value in the body. Do not make the post only a wrapper around a link.
- Engagement prompts should ask a real workflow question, not generic "comment/repost/follow" bait.

## Rewrite Rules

1. One post, one artifact.
2. One hook, one proof, one lesson, one CTA.
3. Use 1-3 hashtags.
4. Avoid "thread" terminology unless there is a real thread.
5. Link the exact artifact that proves the claim.
6. Separate public proof from local/private verification.
7. Keep claims as "working on", "built/prototyped", or "organized" unless the link proves public adoption.
