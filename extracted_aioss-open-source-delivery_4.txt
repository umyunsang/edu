Feature Flags란?
What are Feature Flags?
DEFINITION
"코드 배포 없이 런타임에
기능을 켜고 끌 수 있는 메커니즘"

동적 제어 (Dynamic Control)
코드를 다시 배포하지 않고도 시스템의 동작을 즉시 변경할 수 있습니
다.

조건부 실행 (Conditional Execution)
단순한 if/else 문을 통해 사용자 그룹별로 다른 경험을 제공합니
다.
feature_toggle_example.js
// 기능 플래그를 확인하여 UI 분기 처리
if (featureFlags.newUI) {
// 플래그가 켜져 있으면 새로운 UI 표시
showNewUI();
} else {
// 꺼져 있으면 기존 UI 유지
showOldUI();
}

Feature Flags의 이점
Benefits of Feature Flags

배포와 릴리스 분리
코드를 배포하되 사용자에게는 기능을 숨
김으로써 기술적 배포와 비즈니스 출시를
분리합니다.

즉시 롤백 가능
문제 발생 시 재배포 없이 플래그를 끄는
것만으로 즉각적인 롤백이 가능합니다.

점진적 배포 (Canary)
소수의 사용자에게 먼저 기능을 노출하고
점차 비율을 늘려 위험을 최소화합니다.

A/B 테스팅
동일한 기능의 다른 버전을 사용자 그룹별
로 제공하여 데이터 기반의 의사결정을 지
원합니다.

테스트 in Production
실제 운영 환경에서 내부 사용자나 테스터에게
만 기능을 노출하여 안전하게 검증합니다.

Trunk-Based Dev
긴 기능 브랜치 대신 메인 브랜치에 코드를 자
주 병합하여 통합 문제를 줄입니다.

비즈니스 의사결정 분리
기능 출시 시점을 엔지니어링 팀이 아닌 비즈
니스 팀이 주도적으로 결정할 수 있습니다.

Release Flags (릴리스 플래그)
Safe deployment strategy for incomplete features
PURPOSE
SHORT-TERM
"완성되지 않은 기능을 숨기고,
안전하게 배포하기 위한 플래그"

안전한 배포 (Safe Deployment)
코드를 메인 브랜치에 병합하더라도 사용자에게는 노출되지 않도록 제
어합니다.

점진적 롤아웃 (Progressive Rollout)
기능이 완성되면 소수의 사용자부터 시작하여 점진적으로 전체 사용자
에게 공개합니다.

짧은 생명주기 (Short Lifecycle)
배포가 완료되고 안정화되면 며칠 내지 몇 주 안에 제거해야 합니다.
PaymentController.jsx
// 개발 중인 결제 시스템 V2 숨기기
if (featureFlags.paymentV2) {
// 플래그 활성화 시 새로운 흐름 반환
return <NewPaymentFlow />;
} else {
// 기본적으로 기존 흐름 유지
return <OldPaymentFlow />;
}
//  Note:
// 릴리스가 100% 완료되면 이 분기문을
// 제거하고 NewPaymentFlow만 남깁니다.

Experiment Flags (실험 플래그)
A/B Testing & Multivariate Experiments
USAGE & PURPOSE
"사용자 경험을 비교 실험하기 위해
데이터 기반으로 기능을 분기"
생명주기: 중기 (몇 주 ~ 몇 달)

A/B 테스팅 (A/B Testing)
서로 다른 버전(Variant)을 사용자 그룹에 노출하여 효과를 측정합니
다.

데이터 기반 의사결정
실험 결과를 분석하여 승자(Winner)를 결정하고, 실험 종료 후에는 플
래그를 제거합니다.
ab_test_example.js
// A/B 테스팅을 위한 실험 플래그 확인
const variant =
experimentFlags.checkoutFlow;
if (variant === 'A') {
// A안: 기존 체크아웃 흐름
return <CheckoutFlowA />;
} else if (variant === 'B') {
// B안: 새로운 간편 결제 흐름
return <CheckoutFlowB />;
}
// 승자 결정 후 제거 (Cleanup)

Feature Flags 구현
2. Code-based Management (Rollout & Hashing)
GRADUAL ROLLOUT
"사용자 ID를 해싱하여
일관된 비율로 기능을 노출"
%
롤아웃 비율 (Rollout %)
0%에서 100%까지 점진적으로 노출 범위를 확대하여 리스크를 관리합니다.

일관성 보장 (Consistency)
단순 랜덤이 아닌 userId 해싱을 사용하여, 동일 사용자는 항상 같은 경험을 하
게 됩니다.
FeatureFlags.js
class FeatureFlags {
constructor() {
this.flags = {
newCheckout: { enabled: true, rollout: 20 }, // 20%만 노출
};
}
isEnabled(flagName, userId) {
const flag = this.flags[flagName];
if (!flag || !flag.enabled) return false;
// 사용자 해시값(0-99)이 롤아웃 비율보다 작으면 true
if (userId) {
const hash = this.hashUserId(userId);
return hash < flag.rollout;
}
return flag.rollout === 100;
}
hashUserId(userId) {
// 간단한 해싱 로직 (0-99 사이 정수 반환)
let hash = 0;
for (let i = 0; i < userId.length; i++) {
hash = ((hash << 5) - hash) + userId.charCodeAt(i);
}
return Math.abs(hash % 100);
}
}

0; for (let i = 0; i < exp.variants.length; i++) {

return exp.variants[i]; } } return exp.variants[0]; }

Key Takeaways

배포 ≠ 릴리스
코드 배포와 기능 릴리스를 분리하여 리스크를 최
소화하세요.

즉시 롤백
문제 발생 시 재배포 없이 Flag Off로 즉시 복구
하세요.

점진적 배포
Canary, Ring 배포를 통해 안전하게 사용자 범위
를 넓히세요.

A/B 테스팅
실제 사용자 데이터를 기반으로 비즈니스 의사결정
을 내리세요.

플래그 정리
사용이 끝난 플래그는 반드시 제거하여 기술 부채
를 방지하세요.

Best Practices
6 Core Implementation Guidelines

명명 규칙 (Naming)
의미 있는 kebab-case를 사용하고, 버전 정보를 포
함하여 명확히 식별하세요.

생명주기 관리
플래그의 유형과 목적에 따라 단기/장기 수명을 명확히
정의하세요.

오래된 플래그 제거
기능이 완전히 릴리스되면 플래그를 즉시 삭제하여 코
드를 깨끗이 유지하세요.

모니터링 및 분석
플래그 사용 현황과 변경 사항을 추적하여 운영 가시성
을 확보하세요.

테스트 커버리지
플래그 On/Off 상태에 따른 시나리오를 모두 테스트하
여 안정성을 보장하세요.

문서화 (Documentation)
플래그의 목적, 소유자, 만료일을 문서화하여 팀 내 공
유를 강화하세요.
